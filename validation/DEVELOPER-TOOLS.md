# Chromium developer tools

The browser embeds the original DevTools frontend generated by the pinned Chromium checkout. The native DevTools button beside the address bar opens a developer-tools tab for the active page. F10 and Ctrl+Shift+I also open it when the firmware reports the key combination. Repeating an entry action from the inspected page reuses its tools tab, including when all four tab slots are occupied. The button is disabled inside a tools tab, when the renderer is unavailable, or when a new tab would exceed the tab or tracked-heap limit. Opening tools from the process monitor closes the monitor so the inspector becomes visible.

## Inspector and resource boundary

Each inspected frame owns a Blink `DevToolsAgent` binding. Its tools tab owns a real `DevToolsSession` and forwards Chromium DevTools Protocol messages through Mojo. The session uses Chromium's JSON/CBOR conversion and the original `DevToolsFrontendImpl` compatibility bridge. Closing the tools tab releases the session. Closing its inspected target sends `Inspector.detached`.

The frontend contains 864 generated assets, totaling 19,641,081 bytes before compression and 5,469,980 bytes after compression. `tools/embed-devtools.py` packages only the generated manifest entries. It rejects traversal, duplicate paths, source-root escapes and oversized resources. `devtools_resources.cc` serves them from `https://devtools.uefi.invalid` without network access. Individual decompressed resources are limited to 8 MiB.

The reserved origin does not itself authorize inspection. Only a tools tab created by the native browser receives inspector bindings. Foreign-origin subresource requests are rejected. Authorized tools tabs cannot navigate away from the packaged origin. Responses use a restrictive Content Security Policy and disable caching. Preference values are currently bounded and session-local.

Frontend and inspected page currently share the CPL3 renderer process. Protocol strings are bounded, callbacks use weak references, and the browser-to-renderer inspect command carries tab indices and generations rather than native frame pointers. These measures do not establish complete sandbox or protocol-boundary security.

## Runtime integration

The platform supplies a nestable message loop for Blink Inspector and Chromium's `WebCryptoImpl`. The secure test page checks SHA-256, HMAC verification, AES-GCM round trips and rejection of an altered authentication tag.

`PausePagesPerBrowsingContextGroup` confines a debugger pause to the inspected browsing context group. Chromium's default process-wide pause also suspended this port's frontend because both pages share a renderer. The frontend and target already receive separate group tokens. F1–F12 scan codes now map to Blink function-key events. F10 opens the tools from a normal tab but reaches the debugger as step-over inside a tools tab; F8 resumes execution.

The non-composited frame widget retains a valid `LayerTreeDebugState` for Inspector initialization. The inspector overlay resource pack is embedded, with gzip entries decoded during packaging. The CSS property parser resolves generated `epub…` aliases consistently with property enumeration; otherwise V8's debug property iterator aborts during Console autocomplete.

## Remaining scope

Worker-target attachment, browser Target/Storage/ServiceWorker domains, source-map network loading, persistent preferences, clipboard and file operations are not connected. Profiling, heap snapshots, arbitrary breakpoint placement, step-in/out, complex call stacks and scope expansion, and broad frontend workflows require further execution tests. Unsupported protocol-domain errors remain visible.
